01 / 03 — architecture

How a Vue 3 PWA talks to a .NET Core API

Runtime traffic flows through a Service Worker that caches responses so the app keeps working offline. At build time, the backend's OpenAPI document is turned into typed TypeScript DTOs that the SPA imports.

System map

Runtime + build-time
Primary path
Hot runtime flow: user action → fetch → Service Worker → API.
Secondary path
Internal hops: cache read / write, doc generation, codegen IO.
Build-time
Happens before deploy, not on the wire. swagger.json pulled, DTOs emitted.
Persistent store
Browser-side storage that survives reloads and powers offline.

Reading the map

Five hops

  1. SPA shell never calls the network directly

    Every fetch() from Vue goes through the Service Worker. The SPA stays unaware of online / offline state — it just awaits a response.

  2. Service Worker decides cache vs. network

    Workbox strategies route each request: stale-while-revalidate for read-mostly endpoints, network-first for writes, queued background sync when offline.

  3. API host is a thin .NET Core layer

    Minimal API or Controllers expose endpoints. Domain logic lives behind MediatR handlers. Persistence via EF Core. No knowledge of the SPA shape.

  4. Swashbuckle emits the contract

    At app start, Swashbuckle reflects over the routing table and DTOs, producing /swagger/v1/swagger.json — the single source of truth.

  5. Build-time codegen closes the loop

    CI fetches swagger.json, runs openapi-ts (or NSwag), and writes generated TypeScript DTOs into the SPA repo. The Vue side imports them like any other module — never hand-written, never out of sync.
