02 / 03 — forms & client validation

Catching mistakes before the network hop

Client-side validation is a UX optimisation, not a security boundary. Its job is to make the form feel responsive — surface obvious issues instantly, never wait on the network for things the browser already knows.

Why client validation at all

UX
Instant feedback
A missing required field shouldn't need a 400ms round-trip to surface. The user typed it; the browser saw it; respond immediately.
Saved round-trips
Cheap rules (length, format, regex) reject input before fetch() fires. The Service Worker stays idle; the backend stays calm.
Accessibility
Inline error messages bound via aria-describedby are read by assistive tech as the user moves through fields.
Offline-friendly
Sync rules still work when the PWA is offline. Async rules (server-side uniqueness checks) queue or degrade gracefully.

This is not a substitute for backend validation. The browser is hostile territory — anyone can disable scripts, edit the DOM, or replay requests. Server validation is the real boundary; see page 03.

State flow — schema to UI

Architecture

One schema, one validator, one form state object. Fields read from state; errors flow back from the validator. The component layer is dumb — it renders whatever state the form composable tells it.

Rule taxonomy

What goes where

Pick the cheapest rule that catches the mistake. Push expensive checks (anything async, anything that depends on backend state) into a separate debounced bucket.

Sync · cheap
required · length · regex
Run on every keystroke. Throw the error into errors[fieldName] immediately.
Sync · structural
cross-field rules
Password must equal confirmation. Start date must be before end date. Resolve in schema, not in component logic.
Async · debounced
uniqueness · existence
"Is this email already registered?" Debounce 300ms after typing stops, hit GET /api/users?email=, mark field pending while awaiting.
Server-only
business rules
"Account has insufficient balance." Don't even try to mirror these client-side. Submit, accept the 400, surface the error. See page 03.

Worked component

Vue 3 + vee-validate + Zod

Login form using the schema-driven path. Generated DTO (from swagger.json) supplies the field shape; Zod adds runtime rules; vee-validate exposes reactive state to the template.

// composables/useLoginForm.ts
import { useForm } from 'vee-validate';
import { toTypedSchema } from '@vee-validate/zod';
import { z } from 'zod';
import type { LoginRequest } from '@/api/dto';  // generated

const schema = z.object({
  email:    z.string().email('enter a valid email'),
  password: z.string().min(8, 'at least 8 characters'),
}) satisfies z.ZodType<LoginRequest>;

export function useLoginForm() {
  return useForm<LoginRequest>({
    validationSchema: toTypedSchema(schema),
    initialValues: { email: '', password: '' },
  });
}
<!-- components/LoginForm.vue -->
<script setup lang="ts">
import { useLoginForm } from '@/composables/useLoginForm';
const { defineField, handleSubmit, errors, meta } = useLoginForm();
const [email,    emailAttrs]    = defineField('email');
const [password, passwordAttrs] = defineField('password');

const onSubmit = handleSubmit(async (values) => {
  await auth.login(values);  // see page 03 for the round-trip
});
</script>

DTOs as the schema base

Codegen recap

The Vue side imports types from @/api/dto — generated from swagger.json per page 01. Use these types to constrain the Zod schema so a field renamed in C# breaks the build, not the runtime.

Never hand-write DTO types. If a rule belongs in the contract (max length, enum), put it on the C# DTO with FluentValidation attributes; the codegen will surface it. If a rule is UI-only (visible password toggle state), keep it client-side.
