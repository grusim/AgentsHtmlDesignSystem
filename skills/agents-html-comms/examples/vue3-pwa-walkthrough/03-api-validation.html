03 / 03 — api & backend validation

Trusting only what the server says

Client validation is a UX nicety. Server validation is the boundary that has to hold. Anything that can be tampered with in DevTools — every input, every header, every form payload — must be re-checked on the .NET side before it touches state.

The server owns the contract

Security

The SPA, the Service Worker, and even the generated DTOs all run in territory you don't control. By the time a request hits a controller, every field has to be re-validated as if no client check ever ran. The contract — what's allowed in, what shape comes back — lives on the server.

Two practical commitments:

  • Validate in one place per request. Either FluentValidation pipelines or DataAnnotations + ModelState, never both layered silently.
  • Surface failures as ProblemDetails (RFC 7807). One JSON shape, machine-readable, with field-keyed errors.

FluentValidation on the .NET side

Server

One validator class per request DTO. Registered with DI; the model-binding pipeline invokes it automatically. On failure, ASP.NET returns a 400 with the standard ValidationProblemDetails body — no custom error contract.

// Validators/LoginRequestValidator.cs
public class LoginRequestValidator : AbstractValidator<LoginRequest>
{
    public LoginRequestValidator(IUserStore users)
    {
        RuleFor(x => x.Email)
            .NotEmpty().EmailAddress()
            .MustAsync(async (e, _) => await users.ExistsAsync(e))
            .WithMessage("unknown email");

        RuleFor(x => x.Password)
            .NotEmpty().MinimumLength(8);
    }
}

// Program.cs
builder.Services.AddFluentValidationAutoValidation();
builder.Services.AddValidatorsFromAssemblyContaining<LoginRequestValidator>();

The 400 response shape

Wire format

This is the contract every endpoint emits when validation fails. The errors object is keyed by request field name (matching the DTO property in PascalCase or the JSON name, depending on naming policy).

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

Mapping server errors to form fields

Client

One interceptor in the fetch wrapper. Catches 400 responses, parses problem+json, and surfaces the errors object to whichever form is awaiting the request. Field names must align — see anti-patterns below.

Fetch interceptor

api/client.ts

export async function apiFetch<T>(
  url: string,
  init?: RequestInit,
): Promise<T> {
  const res = await fetch(url, init);
  if (res.ok) return res.json();

  if (res.status === 400 &&
      res.headers.get('content-type')
         ?.includes('problem+json')) {
    const body = await res.json() as ProblemDetails;
    throw new ValidationError(body.errors ?? {});
  }
  throw new ApiError(res.status);
}
Form composable

useLoginForm.ts (extended)

const { setErrors, handleSubmit } = useForm(...);

const onSubmit = handleSubmit(async (values) => {
  try {
    await auth.login(values);
  } catch (e) {
    if (e instanceof ValidationError) {
      setErrors(
        mapServerErrors(e.errors),  // key map
      );
      return;
    }
    throw e;  // not ours → bubble up
  }
});

Anti-patterns

Avoid

Silently duplicating server rules in client schema

Two implementations of "email must end in @company.com" drift apart. Pick one source — the C# attribute or FluentValidation rule — and surface it via codegen or a doc. See page 02 § DTOs.

Trusting client validation as a security check

"The form prevents this" is not an argument. DevTools can change anything. Every input must be re-validated server-side before it influences state.

Custom error envelopes per endpoint

One endpoint returns { errors: [...] }, another returns { failures: {...} }, a third returns plain text. The client interceptor balloons. Use ProblemDetails everywhere.

Returning 200 with errors in the body

HTTP status codes mean things. A validation failure is 400. A 200 with an errors array breaks caches, Service Worker logic, observability, and every standard client library.

Recap
